# PRD-006 — speak both eras, and check remote servers

- **Status:** draft, 2026-11-12
- **Owner:** opencode lane `opencode-ac9958dd`
- **Target release:** 0.7.0 (with PRD-002 E1/E2)
- **Depends on:** PRD-004 (the two scales), PRD-001 (the heal rungs that read the score)
- **Corrects:** PRD-004 §1 and §4, whose premise was checked against the wrong package name

## 1. The correction, with the evidence

PRD-004 concluded on 2026-11-08 that "the published TypeScript SDK does not speak" revision
`2026-07-28`, because `npm view @modelcontextprotocol/sdk dist-tags` returned a single tag,
`latest: 1.32.2`, and `1.32.2` declares `LATEST_PROTOCOL_VERSION = "2025-11-25"`.

That probe read one package name. The TypeScript SDK has been a monorepo of split packages since
2026-04-01, and the 2026-07-28 revision ships in the **v2** line under different names. Verified on
2026-11-12 against the public registry:

```
@modelcontextprotocol/server   latest=2.4.0   (published 2026-04-01, modified 2026-10-23)
@modelcontextprotocol/client   latest=2.4.0
@modelcontextprotocol/core     latest=2.4.0
@modelcontextprotocol/codemod  latest=2.4.0
@modelcontextprotocol/sdk      latest=1.32.2  (v1.x line: bug fixes until ~2027-01)
```

Both v2 packages declare `engines.node >= 20`. The repo's own `zod ^4.6.5` satisfies the v2 peer
range (`zod ^4.2.0`), so no zod bump is required here.

So PRD-004 §4's non-goal — "No attempt to make the SDK speak 2026-07-28. That is upstream's job" —
is no longer a non-goal. Upstream has done it. The doctor's non-goal becomes the opposite: it must not
keep reporting a limitation that no longer exists.

## 2. The problem this actually leaves

Two, and they are different.

**P1 — The doctor cannot inspect a 2026-era server at all.** `src/checker/check-server.ts` builds a
v1 `Client` and calls `client.connect(transport)`, which performs the 2025 `initialize` handshake.
The v1 SDK's newest supported revision is 2025-11-25, so it can never open a 2026-pinned connection.
The estate's own newest server, `starlight-cloud-agents/fleet-mcp`, is on
`@modelcontextprotocol/server ^2.4.0`. The tool that grades the estate cannot grade the estate.

**P2 — The doctor only probes stdio.** `checkServer(command, args)` takes a command and argv.
There is no path for a remote Streamable HTTP server, which is how most servers in the wild are
actually deployed, and how the estate's own fleet is exposed. A doctor that cannot reach a remote
server cannot claim to diagnose MCP.

## 3. Outcome

`mcp-doctor check` and `mcp-doctor score` speak both eras, over both transports, and say which era
and revision they actually spoke. The score header names the revision (PRD-004 R2, R5).

```
mcp-doctor check --url https://tools.example.com/mcp
mcp-doctor check -- command --args "…"
mcp-doctor score --url https://tools.example.com/mcp --revision auto
```

### The era negotiation rule, and why the default is NOT `auto`

The v2 client opts into 2026-07-28 with `versionNegotiation: { mode: 'auto' }`: it probes
`server/discover`, and falls back to the 2025 handshake against a 2025-only server. The upstream
guide is explicit about who must not default to it:

> Who should not default to `'auto'`: spawn-per-invocation CLI and debugging tools. On stdio, a
> legacy server that never answers unknown pre-`initialize` requests stalls `connect()` for the full
> probe timeout before falling back; and the probe round trip changes recorded transcripts/raw logs,
> which matters for tools whose value is byte-stable observation.

`mcp-doctor` is exactly that tool. Its value is a reproducible observation of a server's tool
surface, and it already keeps transcripts and raw stderr. So:

- **Default stays legacy.** A plain `check`/`score` does the 2025 handshake, byte for byte as
  before. No surprise latency, no changed transcripts.
- **`--revision auto` is an explicit flag** that probes and reports the era it reached.
- **`--revision 2026-07-28` is a pin** that refuses to fall back: a 2025-only server is a failure,
  reported as `EraNegotiationFailed`, not silently graded as legacy.

The report states which of the three paths was taken. A silent fallback is a bug.

### Transport rule

stdio keeps its current spawn-and-probe path. Remote servers use `StreamableHTTPClientTransport`
from `@modelcontextprotocol/client` with the v2 request path, plus the OAuth helpers already in
that package for a bearer-token server. The doctor never prints a credential and never stores one.

### The staged migration, in the order the SDK requires

The v1 and v2 packages have different names and can coexist in one manifest. The safe order:

1. Add `@modelcontextprotocol/client` 2.4.0 and `@modelcontextprotocol/server` 2.4.0 while
   `@modelcontextprotocol/sdk` stays installed.
2. Migrate sources directory by directory. Objects must not cross the boundary: a v1 `Client` or
   error instance handed to v2 code fails `instanceof` and nominal checks.
3. Remove `@modelcontextprotocol/sdk` only when nothing imports it.

The codemod (`npx @modelcontextprotocol/codemod@latest v1-to-v2 .`) handles the mechanical renames,
the `package.json` swap, and the `.tool()` → `registerTool()` conversion. It cannot see
repo-local tooling that pins the literal v1 package name, and it does not rewrite anything outside
`src/`+`test/`. Two things in this repo are already known to need hand edits: `test/fixtures/*.mjs`
import the v1 paths, and `pnpm-lock.yaml` carries the v1 resolution.

## 4. Rules

- **R1 — One era per report.** The report names the era (`legacy` | `modern`) and the revision, and
  the revision it was asked to speak. It never blends eras in one score.
- **R2 — Never claim a revision the client did not speak.** `getProtocolEra()` and the negotiated
  version are read from the live connection, not assumed.
- **R3 — No silent fallback.** A `--revision 2026-07-28` pin against a 2025-only server fails
  loudly. `auto` prints which era it reached and why.
- **R4 — The two scales stay.** PRD-004's split holds: `conformance` is binary and revision-scoped,
  `quality` is the estate bar and is labelled as exceeding the spec. A new era adds conformance
  rows; it does not silently reweight quality.
- **R5 — A new era is a new criteriaVersion.** `criteriaVersion` changes when the criteria change
  (PRD-004 R5), so a 2025-era score and a 2026-era score never compare as one trend line.
- **R6 — The doctor grades itself.** PRD-004 R4 stands: the self-score is a CI gate, not a README
  sentence.

## 5. Acceptance criteria

1. `check --url` against a remote Streamable HTTP server returns the same tool surface and the same
   lint issues as `check` against the equivalent stdio server. Fixture pair, byte-compared.
2. A stdio server serving only 2025-11-25 is reachable by the default path with no extra latency
   beyond the existing handshake.
3. `--revision auto` against a 2025-only fixture reports era `legacy` and the revision it fell back
   to, in the header. It does not report `modern`.
4. `--revision 2026-07-28` against a 2025-only fixture exits non-zero with a message naming
   `EraNegotiationFailed`. It does not grade the server as if it had spoken 2026.
5. `--revision 2026-07-28` against a 2026-era fixture reports era `modern` and the negotiated
   revision.
6. The report header names era, revision and `criteriaVersion` on every path (CLI text and
   `--json`).
7. `score --json` emits `{ era, revision, criteriaVersion, conformance: {pass, failures[]},
   quality: {percent, criteria[]}, advisory: [] }`.
8. A 2026-era fixture missing `resultType` produces one advisory and no conformance failure; the
   same fixture under `--revision 2025-11-25` produces neither.
9. `grep -rn "@modelcontextprotocol/sdk" src test package.json` returns nothing. The v1 dependency
   is gone from `package.json` and the lockfile.
10. `npm test` green, except the two documented pre-existing `release.test.mjs` failures (Windows
    GNU-tar reading `C:` as a remote-host spec) and any pre-existing `health.test.mjs` timing race,
    each named as pre-existing with its root cause.
11. The doctor's own `mcp-doctor serve` tool surface still scores 100% on its own quality scale
    after the transport work.
12. No secret, no credential, and no bearer token appears in any report, receipt, log, or fixture.

| M3 | remote Streamable HTTP path | criteria 1, 6, 7 |

M2 is the release. M3 and M4 follow in the same minor. M5 lands with PRD-002 E1, because a
`criteriaVersion` bump and a history file are the same change.

## 7. Non-goals

- No attempt to make the v1 SDK speak 2026-07-28. That is why we migrate to v2 rather than patch.
- No OAuth automation and no credential storage. A bearer token is supplied by the caller and is
  never persisted or printed.
- No change to the seven quality criteria. Reweighting them is its own decision with its own
  evidence.
- No `tasks/*` support. The Tasks extension is deprecated wire vocabulary in 2026-07-28.
